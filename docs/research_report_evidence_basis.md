# 飞控—环境闭环仿真程序的研究依据与项目对应关系报告

日期：2026-07-16  
工程实现对应关系复核：2026-08-20  
范围：本项目中“环境仿真进程—传感器帧—飞控进程—控制指令—环境推进”这一小型闭环程序。  
定位：用于国自然项目申请书中“研究基础/技术依据”的素材，不替代完整立项依据、实验结果或型号鉴定结论。

## 1. 结论摘要

该程序并非任意拼接。其核心结构能够由三类公开研究相互印证：一是软件在环研究采用
控制器与被控对象分离、通过网络交换测量和指令；二是飞行仿真以六自由度刚体动力学、
姿态表示、气动力/力矩和数值积分为物理主线；三是可复现实验平台强调统一调度、数据记录、
回放、批处理和数值诊断[5-11]。项目中的双进程 UDP 锁步、`SensorFrame`/`ControlCommand`
边界、6DOF/RK4、传感器误差、制导—自动驾驶仪—执行机构链，以及日志/回放/多实例工具，
分别可在设计文档和实际代码中找到对应实现。

这里的“有依据”应作严格限定：文献证明的是**架构选择和研究路线具有合理性**，现有测试
证明的是**软件内部行为可重复且满足项目约定**；二者均不能证明当前低阶气动参数、虚拟
执行机构或某一具体飞行对象具有实物精度。项目当前适合定位为可扩展、可回归的闭环研究
工程基线，而非武器级、适航级或经过实飞确认的高保真仿真器。

## 2. 调研方法与证据边界

本次以目录中 4 篇学位论文为起点，补充检索软件在环、飞行仿真框架、6DOF 建模、在线
制导、轨迹数值验证和气动代理数据集。纳入标准为：与本项目至少一个核心模块直接相关；
可从机构、期刊、会议或 arXiv 官方入口核对；全文可公开获取。共纳入 11 篇资料，其中新增
7 篇，原文、BibTeX 和校验信息见 `references/`。

证据强度分为三档：

- **直接依据**：论文所研究的系统边界或技术机制与本项目相同，例如双软件、UDP 和 SIL。
- **方法依据**：数学或验证方法可以迁移，但对象不同，例如固定翼 6DOF 对本项目刚体模型。
- **路线参考**：支持后续研究方向，不构成当前功能或精度证明，例如 AirfRANS 与 Dymos。

## 3. 总体架构依据

### 3.1 双进程软件在环闭环

Prado 等将控制律和飞行器动力学/环境置于不同软件中，两个计算机通过 Ethernet/UDP
交换信息，明确展示了“控制软件—网络—被控对象仿真”的 SIL 结构[6]。平台对象是多旋翼，
控制器是 MPC，因此它不能直接验证本项目的导弹模型或 PNG；但其**进程职责分离、测量与
控制闭环、UDP 交换**与本项目高度同构，是最直接的架构依据。

本项目把这一思想进一步收紧为单向接口对：环境程序只通过 `SensorFrame` 输出测量，飞控
程序只通过 `ControlCommand` 返回命令；在 `LOCKSTEP` 中每一测量帧对应一次计算和一次推进，
`FREE_RUNNING` 则用于软实时节拍和报文故障恢复验证。
这使控制器不能越过传感器边界读取环境真值，并使闭环回归能够按帧重放。该约束记录在
`docs/design.md` 第 3、9、10 和 12 节，实现入口分别位于
`environment_sim/src/env_app.c`、`flight_control_sim/src/fc_app.c` 和
`common/src/protocol.c`。

### 3.2 仿真框架与可复现性

NASA Trick 将模型调度、数值积分、数据记录、检查点/重启及运行时配置作为通用仿真基础
设施[5]。这说明研究型物理仿真不仅是动力学方程，还需要把时间管理、记录和实验复现作为
平台能力。本项目没有复制 Trick，而是在较小范围实现同类关注点：固定仿真时钟、协议版本
与 CRC、运行清单、二进制日志、回放比较、批量统计、工作流 provenance 和逐实例随机种子。相应代码位于
`common/src/sim_time.c`、`common/src/packet.c`、`common/src/logger.c`、
`common/src/provenance.c`、`tools/replay/`、`tools/compare_logs/` 和 `tools/instance_manager/`。

## 4. 环境仿真程序的研究依据

### 4.1 六自由度动力学与姿态推进

Marzouk 给出了非对称固定翼刚体 6DOF 的系统化方程组织，包含平动、转动、姿态四元数、
空气密度、气动力和气动力矩[9]。其具体轴系和固定翼控制面不应照搬，但支持本项目把
“状态—环境力/矩—质量惯量—积分器”作为环境主链的做法。项目通过
`environment_force_model.c` 汇总重力、大气、气动、推进和自转项，再由
`missile_plant_6dof.c` 以 Euler/RK2/RK4 推进位置、速度、姿态和角速度；baseline 采用 RK4。

Sharma 等在 6DOF 火箭着陆轨迹优化中发现，离散转录可能因截断误差和四元数不变量漂移
产生表面收敛但连续动力学不可靠的结果[11]。该研究针对最优控制转录，并非普通前向闭环
积分，因此这里只能作**数值验证方法依据**。它直接提示本项目保留积分器对照、四元数范数
误差、DCM 正交误差和步长敏感性诊断，而不能把“RK4 跑通”等同于全包线可信。

### 4.2 传感器、故障和执行机构闭环

真实飞控只应获得测量而非真值。项目把 IMU、加速度、速度和导引头测量集中构造成
`SensorFrame`，在环境侧加入采样、噪声、量化、延迟、丢包和故障；飞控侧再执行有效性、
时序和健康检查。执行机构状态也归环境所有，以一阶动态、幅值/速率限制和故障脚本作用于
物理模型。对应实现位于 `environment_sim/src/sensor_*.c`、`fault_injection.c` 和
`actuator_model.c`。这一边界与 SIL 的“真实控制代码面对仿真测量和仿真对象”的思想一致[6]，
但当前噪声和故障参数主要是工程基线，尚缺真实器件数据标定。

### 4.3 气动表与代理模型路线

AirfRANS 用高保真 RANS 数据、气动力相关指标以及雷诺数/攻角外推任务评估代理模型[8]。
它不提供本项目飞行对象的气动系数，因而不能验证当前气动模型；其价值是支持“简单模型—
气动表—代理模型”分层和包线外报警的路线。项目已经提供
`aero_model.c`、`aero_database.c`、`aero_database_v2.c` 与 `aero_surrogate.c` 分层接口；
v2 支持高度和双舵偏六维规则网格，并记录模型资源 manifest 和气动包线 flags。
后续必须用目标外形的 CFD、风洞或公开数据替换示例参数，才能讨论
气动精度。

## 5. 飞控程序的研究依据

已有中文学位论文从制导、控制系统和仿真系统角度说明了飞行器制导控制研究通常需要目标/
场景建模、导引信息、制导律、姿态控制、动力学对象和仿真评估的闭环组织[1-4]。本项目在此
范围内采用可解释的模块链：协议校验 → 导航估计 → 模式/健康管理 → 三维比例导引 → 姿态/
角速度自动驾驶仪 → 控制分配 → 命令限幅与保护。代码分别位于
`navigation.c`、`estimator.c`、`guidance_png.c`、`autopilot.c`、`command_manager.c` 和
`safety_monitor.c`。

Kamath 等面向火箭着陆的双四元数制导研究把 6DOF 平动/转动耦合、约束处理、实时求解和
硬件在环验证放在同一制导框架中[10]。它与本项目的三维 PNG 算法不同，因而属于**方法与
验证路线参考**：说明高机动 6DOF 制导最终应检查姿态、角速度、执行机构和状态约束，而非
只比较末端位置。项目当前的自动驾驶仪、舵面分配和保护链为此提供了软件接口，但尚未达到
该论文所述的在线优化或硬件验证水平。

## 7. 可用于国自然申请书的小段描述

本项目拟构建环境仿真程序与飞控软件程序相分离的闭环软件在环验证环境。环境程序统一描述
地球坐标、地形、六自由度刚体运动、气动力/力矩、推进与执行机构动态，并依据真值生成含
噪声、延迟、丢包及故障的传感器测量；飞控程序仅通过标准化传感器帧获取信息，依次完成
导航估计、模式与健康管理、三维制导、自动驾驶仪控制分配及安全保护，再将受限控制指令
反馈至环境程序。两程序采用固定步长锁步推进，从结构上保证“测量—决策—执行—运动”的
因果闭环，并通过日志、回放、批量场景和确定性随机种子实现结果复现。该技术路线与公开
SIL 分布式闭环、通用物理仿真框架和 6DOF 制导研究的基本范式一致[5-6,9-11]；其创新空间
不在重复搭建积分循环，而在统一接口下研究故障条件、模型不确定性和数值误差对闭环性能的
耦合影响。

## 8. 不能越过的结论边界与后续验证

当前证据尚不能支持以下表述：“模型已达到真实型号精度”“闭环性能已经过实飞验证”或
“与成熟工业仿真平台等价”。主要缺口为：

1. 气动、质量/惯量、传感器和执行机构参数尚无目标对象的权威数据标定；
2. 已有真实来源最小 DEM fixture 和工程风模型，但生产级 DEM、权威风场和复杂大气资源尚未形成完整 V6 基准；
3. 虚拟加速度级执行机构仍参与 baseline，舵面气动链尚需控制品质标定；
4. 现有单元/闭环测试主要证明软件约定和确定性，不证明模型真值；
5. 2025—2026 年两篇 arXiv 论文[10-11]尚属预印本，宜用于前沿趋势和方法启发，不宜作为
   唯一的关键结论依据。

建议验证顺序为：解析解与守恒/不变量检查 → Euler/RK2/RK4 与步长收敛 → 独立工具交叉
对照 → 气动/器件数据标定 → Monte Carlo 与故障覆盖 → 半实物/硬件在环 → 条件允许时的
实测数据比对。完成这些步骤后，才能把“架构合理”逐步提升为“定量可信”。
